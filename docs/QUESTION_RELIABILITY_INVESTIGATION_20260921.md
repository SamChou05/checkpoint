# Why quiz generation and answer highlighting were unreliable

Investigation: September 21–22, 2026. Baseline: `7d9cc6a` (current `origin/main` when the investigation began). Three agents independently traced provider contracts, choice semantics, and iOS answer transport/grading. The original local checkout was 28 commits behind and contained unfinished work; all fixes and current-source experiments use an isolated checkout.

## Findings established by code, replay, and current deployment inspection

1. **Native structured output exists but is switched off in TestFlight.** Read-only inspection downloaded the API and worker packages, checked their ZIP digests, and compared seven runtime modules against current main. All fourteen module comparisons match. Both functions were updated September 11 and both still set `BEDROCK_STRUCTURED_OUTPUT_MODE=legacy`. The current worker uses Kimi K2.5 as author and Sonnet 4.6 as solver/reviewer, disabled thinking, 6,000 output tokens, five-question chunks, and six provider calls per job. The synchronous API author is Nova Lite. Native capability is separate from application-side JSON validation; ordinary requests still only ask the model for JSON. [Sanitized deployment snapshot](evidence/question-reliability-20260921/deployed-snapshot.json).

2. **One correct option does not imply three meaningfully different distractors.** For `2 + 2`, choices `4 / 5 / 5.0 / 6` have a single correct answer but two equivalent wrong answers. The exact-string identity check and even truthful per-choice solver judgments permit that. Conversely, `True / true` and `n + 1 / n - 1` must stay distinct in syntax questions. Universal case folding, punctuation removal, or fuzzy string similarity would introduce false rejections. Equivalent-answer assessment must use the question's meaning. [Reproducible offline probe](../backend/bedrock-question-service/evals/checkpoint_choice_reliability_probe.py).

3. **Legacy iOS logic could change a correct structured key into a distractor.** Its explanation helper looked for the substring `correct` and exactly one long choice mentioned anywhere. `Remove the earliest added element is incorrect…` therefore endorsed that distractor in a stack question. Both the sanitizer and grader could replace the correct explicit key; SwiftUI then faithfully highlighted the wrong result. This remains reachable for unverified/local and retained legacy items. Reviewed version-1 questions already use exact answer identity and did not show a shuffle/index defect. The fix removes local prose inference and its contradiction veto while retaining deterministic legacy label decoding. It does not rewrite past attempt snapshots or reconstruct a key already overwritten in a stored question. Member practice excludes these unverified legacy items, but otherwise eligible nonmember legacy inventory can persist until normal retirement/removal. [Detailed reproduction and tests](evidence/answer-highlighting-20260921.md).

4. **Some prior failures were application rejections, not bad model output.** Main already removed cross-question answer-vocabulary deduplication and backend prose-fragment vetoes. The earlier live replay retained 1/4 of the same grammar questions before that fix and 4/4 after. These fixes are now present in both inspected deployed packages. They must not be reported as new fixes or current deployed defects. [Earlier audit](QUESTION_GENERATION_BUG_AUDIT_20260911.md).

5. **The remaining content problems are distinct from formatting and highlighting.** Saved raw outputs contain missing premises, unsupported keys, and explanations inconsistent with the unchanged stem. Current offline replay tests what today's gates enforce; it does not turn historical judgments into new live accuracy estimates. Low temperature, a declared answer key, and agreement among fallible reviewers do not establish a factual proof. Existing tests largely validate behavior given controlled model outputs; passing those tests is not a measurement of real model reliability.

## Fresh experiments and verification

The team made **15 bounded Bedrock calls** across four separately frozen experiments. None changed deployed settings or learner inventory. Captured ordinary responses, exact requests, source/schema hashes, usage, and failures are preserved; reasoning blocks and credentials are excluded.

| Experiment | Observed result | What it establishes |
| --- | --- | --- |
| Native production author → solver → reviewer, two one-question passes | 6/6 calls completed; two arithmetic questions admitted with distinct choices and correct keys | The three stage schemas work on the worker's Kimi/Sonnet pair in this small smoke. It is not a five-question throughput test or a paired legacy comparison. |
| Ordinary-JSON reviewer core versus explicit diversity wording, four calls | 4/4 failed strict formatting because of surrounding prose; diagnostic raw judgments improved on two duplicate controls | Extra instructions did not produce usable structured responses. No recovered JSON was credited as production success. |
| Separate native version of that reviewer comparison | 4 planned, 3 attempted, all 3 schema-valid, only 2 adapter-valid; stopped after failure | Native formatting removed the syntax problem but did not establish semantic or cross-field consistency. |
| Experimental native reviewer v2 with separate accepted/rejected shapes | 2/2 schema- and adapter-valid, but both rejected all eight controls, including three valid questions | The illegal rejection representation was excluded, but useful-answer qualification failed. Production routing remains v1. |

In both usable native reviewer responses, the model accepted wrong alternatives `Three` and `The number three` as distinct enough, despite describing both as the same number in feedback. The explicit diversity suffix did not improve the admitted decisions. The third response recognized this duplicate and returned `valid:false`, but also supplied a nonempty answer and choice feedback. The schema permits those fields independently; the adapter requires them empty for rejection, so it rejected the entire response. That is a concrete gap between **schema-valid transport** and the application's **conditional rejection contract**. The fourth planned call was not made, and no retry replaced the failure.

The tested semantic prompt was **not promoted**. Independent replay confirmed the native adapter outcomes and exact control decisions. Passing feedback length and choice-key checks is not factual validation: even one accepted code-literal explanation overstates that an identifier necessarily raises `NameError`, although an identifier can already be bound.

The follow-up v2 schema encoded accepted and rejected reviews as separate closed shapes. Controlled tests demonstrate mixed accepted/rejected adaptation and exclusion of the captured prohibited field combination. The two live calls, however, admitted no questions: all six appearances of valid controls were falsely rejected. They used the prior experimental diversity prompt, so the evidence does not isolate schema branch selection from prompt interaction. The candidate remains available only to explicit experimental calls; native and legacy production routes retain v1. No additional trial or retry replaced either failure.

See the [native pipeline evidence](evidence/structured-reliability-20260921/PROVIDER_FINDINGS.md), [original distractor diagnostic](evidence/choice-reliability-20260921/README.md), [native follow-up](evidence/choice-reliability-20260921/NATIVE_FOLLOWUP.md), and [failed v2 qualification](evidence/structured-reliability-20260921/REVIEWER_V2_FINDINGS.md).

The initial current-main backend baseline passed all 1,050 tests. Local test setup required Python 3.12, the repository's pinned SDK, and reinstalling the matching optional Chromium runtime; an earlier stale-checkout/browser-environment failure is not a product regression.

The final integrated change passed **1,066 backend tests**, **138 selected iOS simulator tests**, and a final nine-test answer-order regression rerun. The new iOS tests failed with 33 assertions before the fix. Backend lint/compilation, deployment-script tests, SAM template lint/build, and `git diff --check` pass. Each of the three built Lambda artifacts passed seven SDK request-shape checks: six active contracts and one experimental contract, **21 checks total**, with no network calls. All six global/worker mode combinations and invalid-mode failures are covered and were independently reviewed. These package checks establish SDK request compatibility, not provider semantics.

The [local endpoint comparison](evidence/question-reliability-20260921/local-endpoint-binding.json) confirms that the original checkout's configured endpoint belongs to the inspected TestFlight stack. It does not establish installed-app configuration or build overrides. The [seven-day quality-counter query](evidence/question-reliability-20260921/recent-quality-counters.json) found no matching API/worker events, so these experiments do not estimate recent production incidence.

## Changes delivered

- Removed Swift legacy explanation-based key rewriting and contradiction guesses. Grading, correct-answer highlighting, and review references now use the structured key or explicit legacy label mapping.
- Added `QuestionBankWorkerStructuredOutputMode` with `inherit`, `legacy`, and `native` values. The default is `inherit`, preserving current behavior. A worker can now opt into native output while the synchronous API remains legacy. Deployment scripts validate and propagate the setting; rollback can explicitly select worker `legacy`.
- Added reproducible probes, regression tests, and immutable live evidence, including the unsuccessful semantic-prompt and experimental reviewer-v2 trials. Existing main's answer-vocabulary and backend prose-filter fixes were preserved, not reimplemented.

These changes are committed on `codex/question-reliability-investigation`. No backend deployment, mode enablement, model promotion, or cache/history migration occurred. Native output remains off in the inspected deployment.

## Engineering implications

Keep the structured key authoritative through storage, shuffle, grading, and highlighting. Use provider-native schemas to prevent transport-shape failures, and keep counts, answer membership, exact identity, and runtime bounds as deterministic application checks. Neither layer can establish arbitrary-subject factual truth or semantic option diversity by itself.

The separate accepted/rejected shapes experiment shows why schema qualification must measure useful output as well as structural validity. It excluded the prohibited field combination but failed on valid controls, so it was not selected for production. A future candidate needs live accepted, rejected, and mixed-batch qualification. Four required choice slots plus an answer-slot enum could similarly encode count and key membership, while semantic equivalence would remain a separate obligation; that author-schema alternative was not live-tested here.

Any native rollout must qualify every enabled role: the current synchronous Nova Lite route is outside the runtime native allowlist. The new worker override removes that coupling, but the native follow-up shows why this is preparation rather than complete rollout qualification. First/repeated request latency, invalid-item responses, and normal five-question batches still matter. Distinct answer choices, a uniquely supported key, sound explanation, requested difficulty, and admission yield need separate scores; a single 'valid JSON' or 'accepted batch' result conceals different failure modes.

Checkpoint also asks more of a response than a conversational quiz does: an author, independent choice solver, reviewer, conditional feedback contract, and application admission checks must all succeed. Six worker provider calls permit at most two complete three-stage passes. Failures at any stage consume that bounded budget and can leave fewer questions. This explains why a plausible-looking one-shot quiz is not a reliable proxy for admitted production output; it does not excuse avoidable prompt or contract defects.

The user's simple-prompt intuition was also tested in the saved paired author experiment: historically supported keys were 24/30 with a simple prompt and 26/30 with the full prompt. This selected old sample does not prove one prompt better, but it rules out claiming that removing instructions already solved the problem. The current findings support concrete application and transport fixes; they do not establish deterministic arbitrary-subject correctness or a successful semantic-quality intervention.
