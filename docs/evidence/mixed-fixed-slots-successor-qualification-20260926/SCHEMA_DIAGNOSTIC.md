# Fixed-slot native grammar: offline diagnosis and compact successor

The [captured first request](capture.json) used a **5,519-byte** UTF-8 JSON Schema, SHA-256 `316024552a9f67901c652c33ec73a9e311757e4efadd5a7b66bb97666cc2aebb`. It is the same schema pinned in the [frozen plan](plan.json). The service returned `ValidationException` after 0.560 seconds, with no model response. The [read-only CloudTrail diagnostic](VALIDATION_DIAGNOSTIC.md) recovered the decisive service reason: the **compiled grammar was too large**. The request never reached a measurable question-authoring result. An earlier description of this schema as 5,371 bytes was stale; the request and plan both contain 5,519 bytes.

The schema is valid under Draft 2020-12 locally. All eleven internal references resolve, all seventeen object definitions have `additionalProperties: false` and require their declared properties, and it uses none of the features that [Bedrock documents as unsupported](https://docs.aws.amazon.com/bedrock/latest/userguide/structured-output.html), such as recursive schemas, external references, numeric or string range constraints, or open `additionalProperties`. The exact request also passed the SDK shape check. These checks cannot establish that Bedrock's compiled grammar fits its service limit. AWS documents a supported subset and grammar compilation, but does not publish a threshold that would let this local validator predict this rejection.

The preceding accepted constructed-author call used the same Sonnet 4.6 model, `maxTokens: 16000`, adaptive thinking, high effort, and Converse/outputConfig transport. Its schema was 3,089 bytes with three definitions, four references, three `anyOf` nodes, and fifteen `enum` nodes. The rejected mapped schema had six definitions, eleven references, four `anyOf` nodes, and thirty-five `enum` nodes. The new grammar repeats skill/objective/topic singleton enums in separate mapped prose and quantitative branches and makes five slots point at those branches. Byte length alone is not the service's compiled-grammar size, so these counts explain a plausible source of growth rather than isolate a single offending construct. The earlier count-bound five-slot solver and reviewer calls also show that numeric property names and closed required slot maps can work with Bedrock; those features alone are not a reason to remove cardinality enforcement.

Offline alternatives, serialized compactly with the same definitions for numerical tasks and prose questions:

| Shape | UTF-8 bytes | `$ref` | `anyOf` | `enum` | Tradeoff |
| --- | ---: | ---: | ---: | ---: | --- |
| Captured mapped row per skill | 5,519 | 11 | 4 | 35 | Rejected by Bedrock grammar compiler. |
| Shared tagless row in five fixed slots | 3,025 | 9 | 3 | 14 | Smallest source change, but each slot still accepts either prose or quantitative content; local code must reject the wrong type. |
| Separate tagless quantitative/prose row definitions | 3,018 | 9 | 2 | 14 | Schema enforces the 3:2 row types, but retains wrapper objects and another reference layer. |
| **Direct typed slots** | **2,601** | **7** | **2** | **12** | Slots `0`–`2` contain task objects; slots `3`–`4` contain prose-question objects. The trusted adapter wraps rows and injects metadata. |

The direct typed-slot design keeps `questions` a closed object with exactly five required keys. The first three keys reference the existing quantitative task definition; the last two reference a prose-question definition containing prompt, four choices, correctChoice, explanation, and difficulty. It omits model-written `topic`, `skillID`, `objectiveID`, `objective`, and fixed format fields. The server derives those fields from the validated, scope-digested request's exact slot assignment, not from the model or the slot text. Its local Draft 2020-12 fixture accepted all five valid slots and rejected a missing slot, an extra slot, prose in an arithmetic slot, a task in an English slot, a forged skill ID, and a model-written answer key inside an arithmetic task. This is a prospective design, not a source change or a Bedrock acceptance result.

The adapter must preserve the raw provider object, schema hash, original slot ordinal, trusted assignment and injected fields in provenance before compilation and review. Top-ups must bind each remaining original slot to that original assignment; simply labeling returned rows in order would silently misattribute work. Locally reject unknown provider fields as well as scope/difficulty/content mismatches. In particular, a correct skill ID copied from the request does not prove that the English question tests the assigned objective. Numerical learner content and key must still come from the deterministic compiler. English answer choice, key, explanation and distinctness still require independent solver, reviewer and pairwise content checks. No JSON grammar can prove their semantic correctness by itself.

The smaller schema is **unproven at Bedrock**. A successor would need a new isolated candidate, frozen exact request/schema/prompt, socket-blocked tests, one bounded provider trial, and the same blind answer and choice-pair gates before considering promotion. The failed five-slot capture must not be rerun or treated as quality evidence.
