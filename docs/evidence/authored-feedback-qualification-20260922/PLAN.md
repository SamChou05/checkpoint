# Immutable authored-feedback audit qualification — preparation only

This new experiment tests the actual inactive runtime audit on the unchanged 24 learner payloads from `final-content-audit-20260922/adversarial-plan.json`. All are previously exposed diagnostic controls. Their original 12 accept and 12 reject decisions, exact text, batch order, choice order and task scope remain immutable. Near-duplicate paired variants remain together. This is not fresh-worker or author/solver qualification.

Four sequential provider requests contain six controls each. They use `/tmp/checkpoint-authored-feedback-integration/backend/bedrock-question-service`, its `FULL_FEEDBACK_AUDIT_SYSTEM_PROMPT` including the difficulty rubric, `AuthoredFeedbackReviewContract(6)`, and actual pure `build_input`, native adapter, `validate` and `accepted_indices` functions. A changed runtime or transport schema requires a newly reviewed draft before freezing. The input retains main and all four exact feedback slots, but hides the explicit author key, difficulty, gold, prior decisions and case provenance. Authored teaching may still reveal the intended answer.

Settings are Sonnet 4.6 (`us.anthropic.claude-sonnet-4-6`) in `us-east-1`, adaptive thinking, high effort, 16,000 shared tokens, no temperature, connect timeout 3 seconds, read timeout 75 seconds, and SDK total maximum attempts 1. No inference occurs when building or testing a plan. No retries, warmups, continuation, repair, rescue, replacements or question-bank writes are permitted.

Primary prospective criteria are four structurally valid `end_turn` calls, each finishing its provider call within 75 seconds; all 24 frozen admission decisions correct, comprising 12 sound retained and 12 defective rejected; and exact-original selected learner payloads. A malformed batch earns no structural or semantic batch credit. The full 4-call, 24-item, 144-reason denominator survives a hard stop. Provider, stop-reason, elapsed-time, native-schema, local bound/type/identity or binding failure ends the trial. Semantic errors alone do not stop the other planned batches.

Difficulty is recorded as an independent diagnostic. The content test passes an explicitly permissive predicate to the actual gate, so a difficulty disagreement cannot explain away an admission error. This does not qualify the production difficulty policy, target difficulty, worker budget, yield or complete three-stage pipeline.

Task, answer and each of the five feedback labels are compared with `authored-feedback-20260922/known-control-field-expectations-draft.json`. Its two interpretation-dependent field expectations stay explicit: true mathematical bus facts versus implied minimum exclusion, and style-sensitive semicolon-before-and feedback. Neither caveat changes original admission gold. All 144 returned task/feedback reasons require independent factual and exact-item-grounding review, including the reasons in wrongly admitted cases; label agreement does not establish reason accuracy. These metrics are reported separately from the primary learner-content criteria. No prior all-reasons-perfect trial is relabeled or rescued.

Capture retains exact frozen provider requests, returned JSON text, usage when available, stop reasons, timing, strict native/local status, every assessed row, and hashes plus exact copies of selected originals. Provider `reasoningContent` text and signatures, response headers and arbitrary metadata are never saved. Errors retain only a bounded type, AWS code (128 characters), safe message (2,000), HTTP status and request ID (128), with known credentials and common token forms redacted. Missing usage is unavailable, not zero. The capture never stores `str(error)` or an exception stack.

Preparation and dispatch are separate. `--draft` writes only `plan-draft.json`, marked unapproved. After root confirms runtime source is final and reviews the draft, `--freeze REVIEWED_DRAFT_SHA256` checks all current bindings and exclusively creates `plan.json`. A separate explicit root authorization is required to dispatch `--execute APPROVED_FROZEN_PLAN_SHA256`. Execution rechecks the frozen plan, runtime/evidence/harness hashes, input identity and exact requests before obtaining credentials or creating the SDK client. Existing capture paths cannot be resumed or overwritten.

The harness's unit tests use fake clients only. Handcrafted oracle rows check schema, exact input bindings, gate consistency and unchanged outputs; they are not provider judgments or semantic qualification. Tests exercise all four batches, failure stops, source drift, native versus local failures, deadline boundaries, no-retry limits, safe errors, reasoning omission, and preserved denominators.
