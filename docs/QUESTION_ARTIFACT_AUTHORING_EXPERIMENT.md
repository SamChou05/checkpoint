Status: author stage frozen before dispatch, September 8, 2026 UTC; no calls or results are claimed by this document. This trial asks whether an author can propose useful subject exercises whose displayed artifact and measured answer share one exact representation. It does not change production generation or qualify a general correctness gate.

## Four fresh exercises, two author calls

One author call requests two Python candidates; one requests two HTML candidates. These are two fresh batches within already-studied subject families, not two previously untested domains. There are no retries, JSON repairs, replacement candidates, top-ups, model solvers, model reviewers or feedback-rewriting calls. Every raw candidate and every rejection remains in the denominator. There is no matched ordinary-author arm, so this is a construction-feasibility trial, not a causal estimate of improvement over the existing pipeline.

The fixed author configuration is `us.anthropic.claude-opus-4-6-v1` with adaptive thinking, high effort and 16,000 maximum output tokens; one SDK attempt, three-second connection timeout and 100-second read timeout. The executable plan enforces at most two dispatches, 32,000 UTF-8 input-text bytes per call and 64,000 total. Bytes are not tokens or a certified spend cap. It may use at most two existing managed Python execution sessions and two isolated browser observations, one observation per eligible candidate. Unused allowance cannot be transferred to replacement questions. These experimental deadlines are not deployed-worker qualification.

Python jobs require CPython 3.12.13, the previously observed managed version; a different observed version is unsupported and cannot be relabeled. The existing managed transport is limited to two sessions and two invokes, 90 seconds for the run, 30 seconds per candidate including a five-second cleanup reserve, and a separate 60-second service session TTL. Its capture allows 16 events and 32 KiB per operation. The execution harness retains its existing two-second wall/CPU, 256 MiB memory, 4 KiB output/result and 64 KiB transport ceilings. The isolated HTML observer has a 10-second browser-launch timeout, three seconds per operation and each cleanup, a 16 KiB input limit, 32 KiB output limit, and 4,096-character DOM limit. Its parent must enforce a 45-second whole-process deadline, retain bounded output, and stop subsequent observations if cleanup is not confirmed. Each HTML job records the actual Chromium version and exact observer source hash. The native plan binds exact generated artifacts before native dispatch; the author plan freezes the adapters before author dispatch.

The author receives the learning goal, inspected source summaries and the family schema, including its supported operations and complete-field length limits. It supplies the artifact, typed alternatives and proposed teaching explanations. It does not supply an authoritative key, a free-written replacement stem or a verification certificate. It may propose a difficulty rating; that rating supplies no evidence of challenge. No prewritten specimen question, expected native result or assessment-only pass/fail label is supplied to the author.

## Exact construction and acceptance boundary

The application renders the complete artifact, operation and options from the same structured candidate that goes to the native adapter. The existing limits remain **320 characters for the full stem, 140 per choice, 420 for the main explanation and 280 per choice explanation**. Main and per-choice feedback must also contain at least 12 characters after trimming. These include task wording, source delimiters and any displayed invocation. A field that does not fit is rejected without clipping facts, removing whitespace, shortening an explanation or silently changing the operation. Preserve raw and rendered forms and their exact content identities.

For Python, the observation contract distinguishes an expression's value from a script followed by an explicit function invocation. The latter must display its entry point and exact supplied arguments as well as the complete source. Options represent supported typed return values or an exact exception class; output on stdout is not a return value. The application renders option text and derives a key only when exactly one offered alternative matches a completed eligible observation. An intentionally erroneous program can have a valid exception answer. An exception caused by an unsupported restricted environment, a timeout or a serialization failure is not evidence of an ordinary Python exception answer. No model-written snippet, replacement input or repaired indentation can inherit the original item's observation.

The trusted runtime version is declared by the experiment, displayed with the Python task and checked against the completed observation. Typed result comparison must preserve distinctions such as Boolean versus integer and tuple versus list; a serialization format cannot silently redefine the language value being tested. Hashes bind exact bytes and operation metadata, not a claim that two differently written programs are equivalent.

For HTML, the candidate supplies literal markup, an exact target identifier and an ordered list of supported native Boolean properties. The application displays the source and the precise property query and renders the four Boolean-tuple options itself. The observer loads that same literal source under its recorded parsing context, locates exactly one target and reads precisely those properties in order. Any document wrapper or setup capable of affecting the answer must be fixed in the contract and apparent in the task. There is no model-supplied query JavaScript or hidden DOM mutation. An author cannot replace a native property with a similar-sounding one: the `disabled` property, effective disabled state, validation eligibility and current validity are distinct observations.

Exact typed-value uniqueness and distinct displayed choices are both required. Reject ambiguous renderings, unsupported types, missing or multiple targets, unmatched answers and multiple matching alternatives. A successful source hash or native response alone does not authorize an item. A native key disagreement cannot be repaired by selecting the author's intended option, inserting a fifth option or rewriting its explanation.

The key is mechanically bound to the observed task; **causal explanations remain claims to assess**. A template saying which tuple or return value was observed can be correct yet educationally weak. If the author proposes a causal explanation, inspect it in full, including all distractor reasons. No authored explanation gains trusted status just because its associated choice matches the observation. Neither family emits a production verification version or updates mastery.

## Source-backed learning targets

The source packets should establish semantics without prescribing final questions. Prefer compact cases in which the details change the result and the alternatives reflect different plausible interpretations.

| Family | Suitable interaction | What the learner must distinguish |
| --- | --- | --- |
| Python | A shared nested list, a slice copy and a subsequent mutation, observed through a finite returned value | Copying an outer container versus sharing contained objects, and mutation versus rebinding |
| Python | Conditional accumulation with a loop exit and a loop `else` | The actual path through the data and whether the loop terminates through `break` or exhaustion |
| HTML | A first-legend exemption within another disabled ancestor | Which particular ancestor's exemption applies, rather than treating one exemption as global enablement |
| HTML | Inherited disabled state with required/type constraints, observed through distinct validation properties | Attribute presence, effective disabledness, eligibility for checking and whether an underlying constraint is satisfied |

Python's documentation describes names sharing mutable objects, and the sequence reference explains repetition and shallow copying; these support tracing changes in the displayed object graph, not inferring identity from a serialized result. Its control-flow guide specifies when a loop's `else` executes. These are candidate topic directions, not instructions to reproduce documentation examples or a guarantee that any resulting question earns level 3. [Names and objects](https://docs.python.org/3.12/tutorial/classes.html#a-word-about-names-and-objects), [sequence operations](https://docs.python.org/3.12/library/stdtypes.html#common-sequence-operations), [loop control](https://docs.python.org/3.12/tutorial/controlflow.html#else-clauses-on-loops).

The HTML Standard defines disabledness using the element's own attribute and disabled ancestor fieldsets, with an exception for the first legend of the particular fieldset. Disabled controls are barred from constraint validation. Validation eligibility and validity flags answer different questions, and checking validity consults eligibility as well as constraints. These distinctions support scoped teaching explanations; a browser result alone cannot establish accessibility compliance or whether a whole form submits successfully. [Disabled controls](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#enabling-and-disabling-form-controls:-the-disabled-attribute), [constraint validation API](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#the-constraint-validation-api).

## Assessment and prospective success criteria

Before revealing model explanations, proposed difficulty or the derived key, an independent assessor receives every renderable candidate's exact stem and choices, goal and relevant source packet. Freeze all warranted answers, completeness, distinctness, distractor plausibility, goal fit and a 1–5 difficulty estimate with a concrete rationale. Where tools help that independent assessment, retain the exact submitted artifacts and observations separately; never repair a displayed program or silently reinterpret an HTML operation. Additional text variants receive separate identities with joins back to the same authored candidate, not extra sample credit. Unrenderable raw records remain explicit failures or unsupported attempts.

Use the shared cognitive rubric. Level 3 requires interpreting evidence or a representation to distinguish plausible conclusions, with scenario details affecting the answer. A long trace, specialist vocabulary, two API names or a model-assigned number is insufficient. An item solvable by one familiar rule without interpreting the case is level 2. The target is at least 3, not an automatic promotion to 4 merely because several operations occur. These independent assistant ratings are provisional judgments, not educator consensus, calibrated item difficulty or measured learning gains; report disagreements rather than averaging them away.

After that record is frozen, join the native key and assess the main explanation and all four choice explanations. For each distractor, distinguish a result contradicted by this exact execution from a false universal statement about the language or platform. A plausible misconception is an assessment of the alternative, not proof of what caused a learner to select it. Repetition of the correct value without an explanation does not satisfy the teaching criterion.

Full feasibility success requires **all four planned candidates**, with two in each family, to meet all of these conditions:

1. The complete task survives unchanged into a supported native observation, with exactly one warranted, distinctly rendered option and an exact key match.
2. Every premise needed for that answer is displayed or part of the explicitly scoped language/platform semantics; no repair, hidden setup or unjustified generalization is needed.
3. All three distractors are distinct and plausible for the intended skill, with no second valid representation of the key or irrelevant filler.
4. The main explanation and all four choice explanations are supported and sufficiently informative to teach the relevant distinction.
5. Independent assessment rates the actual item at least 3 and finds substantive fit to its learning goal; every complete field fits the unchanged limits.

Report these components separately, along with mechanically constructed, unsupported, content-rejected and fully usable counts out of four. One useful item per family is a partial construction signal, not success on the requested target. A correct key with weak distractors or faulty teaching feedback is not a usable question. A too-easy or overlong item is not evidence that the system caught a factual error. No excluded item may be replaced to improve the denominator.

## Capture, stopping and limits of inference

Freeze exact prompts, source summaries and provenance, schema/rendering rules, native adapters, module hashes, settings and job order before dispatch. Persist each actual author request before sending it; retain returned final text, stop reason, known token usage, elapsed time and reasoning-block count without private reasoning text. Missing usage remains unknown. Persist exact native submissions, source/input/query hashes, runtime versions, correlated observations and cleanup records. Retain raw proposals and every admission reason even if no question is constructed.

Before live dispatch, bounded offline checks must show that stale observations, changed source/input/query, reordered property results, duplicate-equivalent option renderings and runtime mismatches cannot produce an accepted binding. Include an intentionally invalid program with its correct exception alternative and a valid result that differs from a repaired program. These tests qualify the construction boundary, not the four future questions' teaching quality.

Provider or malformed-envelope failure, a correlation mismatch between a dispatched artifact and its observation, native operational failure, or failed cleanup stops further dispatch; a partial run remains partial. A well-formed but unsupported, overlong or semantically defective candidate is recorded without retry and does not become a false-answer success. Content defects block any qualification while remaining available for complete assessment of already-authorized candidates. No automatic model escalation, new permissions, deployment or production inventory write is part of the trial.

Even a full pass would establish only that four fresh exercises in two observable subject families can be constructed with useful content under these limits. It would not prove arbitrary Python equivalence, universal HTML conformance, program complexity, source-to-rule translation, general factual correctness, adaptation over time or app-blocking behavior. The old all-pairs failure remains outside this finite-observation contract; changing its task into a finite output question would be a different exercise, not a fix to the historical claim. Arbitrary learning goals remain the product scope. Extending this mechanism requires appropriate evidence for each claim type and measured useful coverage, rather than renaming all learning as executable tracing or formal logic.
