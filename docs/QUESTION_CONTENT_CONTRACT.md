# Question content identity and relevance filtering

The server and iOS client use the same conservative choice identity: canonical Unicode composition (NFC) and trimming surrounding whitespace. Case, diacritics, mathematical symbols, musical accidentals, labels, inflection, word boundaries and internal whitespace remain significant. For example, `True` differs from `true`, `si` from `sí`, and `D F A C` from `D F# A C`. Canonically equivalent Unicode encodings of `café` remain duplicates.

A question requires four nonempty, distinct choices and an expected answer that occurs in those choices. The backend rejects a missing expected answer instead of inserting a new option. It rejects overlong choices instead of truncating content. Single letters can be valid answers, including notes or letter recognition; letters are not rejected merely because they could also be option labels. The verified iOS path grades the exact chosen text; legacy positional answer resolution first checks for a literal matching choice so a decimal or a leading letter cannot override actual content.

Deterministic identity does not establish semantic equivalence. Two differently worded options may express the same answer, and two nearly identical options may differ in a crucial qualifier. The independent semantic review must judge whether exactly one option is correct. The previous 90%-prefix rule is removed: a final `except Jo` can change the truth of a claim. Generic filler detection keeps a separate prose-matching helper; it cannot supply choice identity.

Choice-set and topic-answer history keys use length-delimited components so literal pipes or colons cannot create collisions. Request and generated history preserve internal answer whitespace.

The study-coaching filter recognizes explicit requests for personal study plans, study schedules, or advice after missing a quiz. It no longer treats words such as “next step,” “motivation,” “distraction,” or “finish line” as sufficient evidence of off-topic content. These can themselves be the subject of a legitimate question. Less explicit relevance judgments remain the semantic reviewer's responsibility, and study-skills goals retain the existing exemption.

The shared [contract fixtures](../backend/bedrock-question-service/tests/fixtures/choice_identity_contract.json) run in both the backend and iOS tests. They cover Unicode equivalence, preserved distinctions, eight subject questions, six legitimate subject prompts, and five explicit coaching prompts. iOS additionally checks that every displayed choice grades correctly after sanitization and shuffling, for both verified and legacy records. These tests establish content preservation and structural behavior, not the factual accuracy of arbitrary generated questions.

## Stem and source preservation

A separate September 6 regression reproduced actual corruption before review: a multiline Python stem arrived as one line; a source lost the indentation required by Python and changed `print("a  b")` into `print("a b")`. The original source parsed, while the source given to the reviewer raised `IndentationError`.

Subject content now has a different contract from compact metadata. Backend and iOS normalize CRLF/CR to LF, replace control characters other than tabs/newlines with spaces, and remove empty boundary lines. They preserve leading indentation on nonempty lines, tabs, repeated spaces, blank lines inside the text and original Unicode code points. Titles and document names keep their existing compact formatting. Original Unicode matters in sources because a code example can test string length.

The backend preserves the stem through sanitization and history into author/reviewer JSON. The iOS importer, persistence, outgoing request and received-question sanitizer preserve the same content. Document deduplication uses the exact UTF-8 content, so case or quoted spacing cannot merge different sources. Redundant final choice lines may be removed only when their text matches the choices, optionally preceded by the matching ordinal label. The remaining stem keeps its layout. Existing length budgets and explicitly marked source truncation remain; overlong stems are rejected instead of silently cut.

The [shared subject-content fixtures](../backend/bedrock-question-service/tests/fixtures/subject_content_contract.json) exercise these paths. Backend tests parse the preserved Python and inspect the exact double-space string literal, and iOS tests cover file import, persistence, request encoding, question decoding, sanitization and grading. This fixes a demonstrated input-corruption issue; it does not establish correctness of arbitrary model-generated questions.
