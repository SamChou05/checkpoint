# Question content identity and relevance filtering

The server and iOS client use the same conservative choice identity: exact Unicode code points after trimming only ASCII boundary whitespace. Case, diacritics, mathematical symbols, musical accidentals, labels, inflection, word boundaries and internal whitespace remain significant. For example, `True` differs from `true`, `si` from `sí`, and `D F A C` from `D F# A C`. Canonically equivalent Unicode encodings also retain their distinct original bytes: composition can change a code literal's value.

A question requires four nonempty, distinct choices and an expected answer that occurs in those choices. The backend rejects a missing expected answer instead of inserting a new option. It rejects overlong choices instead of truncating content. Single letters can be valid answers, including notes or letter recognition; letters are not rejected merely because they could also be option labels. The verified iOS path grades the exact chosen text; legacy positional answer resolution first checks for a literal matching choice so a decimal or a leading letter cannot override actual content.

Deterministic identity does not establish semantic equivalence. Two differently worded options may express the same answer, and two nearly identical options may differ in a crucial qualifier. The independent semantic review must judge whether exactly one option is correct. The previous 90%-prefix rule is removed: a final `except Jo` can change the truth of a claim. Generic filler detection keeps a separate prose-matching helper; it cannot supply choice identity.

Choice-set and topic-answer history keys use length-delimited components so literal pipes or colons cannot create collisions. Swift uses UTF-8 `Data` keys, because its `String` equality ignores canonical Unicode differences. Request and generated history preserve internal answer whitespace and Unicode sequences.

The study-coaching filter recognizes explicit requests for personal study plans, study schedules, or advice after missing a quiz. It no longer treats words such as “next step,” “motivation,” “distraction,” or “finish line” as sufficient evidence of off-topic content. These can themselves be the subject of a legitimate question. Less explicit relevance judgments remain the semantic reviewer's responsibility, and study-skills goals retain the existing exemption.

The shared [contract fixtures](../backend/bedrock-question-service/tests/fixtures/choice_identity_contract.json) run in both the backend and iOS tests. They cover preserved distinctions, nine subject questions, six legitimate subject prompts, and five explicit coaching prompts. iOS additionally checks that every displayed choice grades correctly after sanitization and shuffling, for both verified and legacy records. These tests establish content preservation and structural behavior, not the factual accuracy of arbitrary generated questions.

## Unicode answers and feedback

A September 6 regression demonstrated a valid multiple-choice question being changed into one with no correct choice: the expected Python literal contained an `e` followed by a combining acute accent, and its evaluated string length was 2. NFC normalization rewrote both the expected answer and the offered choice to a composed `é`, whose length was 1. All distractors also had length 1. The sanitizer now preserves that original two-code-point literal; tests independently parse and count the surviving answer rather than merely comparing identity keys.

Expected-answer membership and grading use exact UTF-8 identity after ASCII boundary trimming. A composed expected answer cannot match a decomposed offered choice. Legacy positional/cue compatibility cannot repair such an unoffered canonical alias. Feedback lookup and filtering also compare exact keys, so a Unicode variant cannot borrow another answer's explanation.

One choice set cannot contain two alternatives that Swift regards as canonically equivalent: its current String-keyed choice UI and feedback dictionary cannot represent that pair safely. Both backend and iOS reject such sets without rewriting either alternative. NFC is used only to detect this representation ambiguity on the backend; it never supplies an answer identity. Distinct questions containing a single composed or decomposed alternative remain independently usable, including in saved answer and choice-set history.

Swift's JSON decoder merges canonically equivalent object properties before exposing them to custom decoding. Question-response and saved-snapshot entry points therefore inspect raw JSON through `NSDictionary` first, rejecting colliding `choiceExplanations` properties before decoding can attach the wrong value. Generation, bank claims, Apple Foundation responses, primary/backup snapshots and legacy snapshot loading use this check. Valid feedback keys retain their original bytes; malformed snapshots follow the existing backup-recovery path. The wire schema, persistence schema and stem fingerprint versions are unchanged. Previously rewritten choices cannot be reconstructed without their original content.

## Stem and source preservation

A separate September 6 regression reproduced actual corruption before review: a multiline Python stem arrived as one line; a source lost the indentation required by Python and changed `print("a  b")` into `print("a b")`. The original source parsed, while the source given to the reviewer raised `IndentationError`.

Subject content now has a different contract from compact metadata. Backend and iOS normalize CRLF/CR to LF, replace control characters other than tabs/newlines with spaces, and remove empty boundary lines. They preserve leading indentation on nonempty lines, tabs, repeated spaces, blank lines inside the text and original Unicode code points. Titles and document names keep their existing compact formatting. Original Unicode matters in sources because a code example can test string length.

The backend preserves the stem through sanitization and history into author/reviewer JSON. The iOS importer, persistence, outgoing request and received-question sanitizer preserve the same content. Document deduplication uses the exact UTF-8 content, so case or quoted spacing cannot merge different sources. Redundant final choice lines may be removed only when their text matches the choices, optionally preceded by the matching ordinal label. The remaining stem keeps its layout. Existing length budgets and explicitly marked source truncation remain; overlong stems are rejected instead of silently cut.

The [shared subject-content fixtures](../backend/bedrock-question-service/tests/fixtures/subject_content_contract.json) exercise these paths. Backend tests parse the preserved Python and inspect the exact double-space string literal, and iOS tests cover file import, persistence, request encoding, question decoding, sanitization and grading. This fixes a demonstrated input-corruption issue; it does not establish correctness of arbitrary model-generated questions.

## Versioned stem identity and saved-history compatibility

Preserving the displayed stem was insufficient while duplicate detection still folded its contents. Three valid Python pairs demonstrated the collision: moving a print outside a loop changes output from `1` then `3` to just `3`; `len("a  b")` and `len("a b")` produce 4 and 3; composed and decomposed Unicode literals that display as `é` produce lengths 1 and 2. Each pair had the same old fingerprint despite having different answers.

Version 2 stem identity normalizes CRLF/CR to LF and trims only ASCII boundary whitespace (space, tab, newline, carriage return, vertical tab and form feed). All other code points remain exact: case, indentation, quoted spaces, punctuation, presentation prefixes and Unicode composition are significant. This is an identity contract, distinct from the subject-content control-character cleanup above. Swift uses UTF-8 `Data` keys because `String` equality considers canonically equivalent Unicode sequences equal. Both implementations hash the exact UTF-8 bytes with the existing 64-bit FNV-1a algorithm and return 16 lowercase hexadecimal characters.

The request field `stemFingerprintVersion` identifies how to interpret `blockedStemFingerprints`. Only integer values 1 and 2 are accepted; an absent or null field retains version 1 behavior for older clients and queued requests. The updated iOS client sends version 2 for direct generation, bank ensure and claim. Ensure stores the version with the blocked list in `generationRequest`, including when updating an existing bank; workers and generation top-offs retain it. Neither control field is sent to the model. Fingerprint count and format limits are unchanged.

New inventory comparisons always use version 2 identity, independently of the incoming history-token version. New remote question IDs use the `:stem:v2:` UUID namespace component to avoid the old lossy stem-ID collisions. Existing question IDs and claim IDs remain readable and unchanged; duplicate detection recomputes identity from the actual stored `questionJSON.prompt`, rather than trusting a previously cached stem fingerprint. Claims interpret incoming blocked tokens under their declared version, and replay still returns the originally committed claim result. Exact duplicate stems remain suppressed during sanitization, inventory insertion, claims and local checkpoint sessions.

Old version 1 hashes cannot be converted to version 2 without the original prompt. They retain their original interpretation and their known false collisions; they are never silently treated as version 2. Updating iOS recomputes version 2 history from saved question prompts. Previously discarded questions cannot be recovered from a fingerprint alone. Deploy the version-aware backend before releasing the version 2 client; new-client/old-server compatibility is not guaranteed. This milestone performs no deployment or bulk data migration.

The [shared stem-identity fixtures](../backend/bedrock-question-service/tests/fixtures/stem_identity_contract.json) contain the reproduced outputs and golden hashes. Tests cover distinct code-pair IDs, exact repeat suppression, saved legacy rows with stale hashes, old-client/new-server requests, updated-client/legacy-row claims, claim replay, ensure upgrades, worker loading, generation top-offs and the local session path. These checks establish the deterministic identity and compatibility behavior; cosmetic prose equivalence remains a semantic-review concern.
